# Direct2Logbook mobile

React Native / Expo SDK 58. Use Expo Go for the first simulator run; development
builds are available when working on native integrations. JavaScript bundles
alone do not verify that either emulator has launched the app.

## Start on this Mac

```bash
cd /Users/blakepowell/react_native/d2lb
./scripts/mobile go
```

Keep that terminal open. In Metro's terminal press **i** for Apple Simulator or
**a** for Android Emulator. Expo CLI installs the matching Expo Go client when
needed. If a device is not running:

- **iOS:** Xcode → Open Developer Tool → Simulator. Complete Apple's component
  and iOS runtime downloads, then choose an iPhone under File → Open Simulator.
- **Android:** Android Studio → More Actions → Virtual Device Manager (or
  Tools → Device Manager). Start `Pixel_10_API_36` with the play button. It uses ARM64 Android 16 and software graphics.

The launcher uses an ignored `.local-node-path` file on this checkout to select
Node 24 without changing your existing shell aliases. On another machine use
`.nvmrc` with `nvm install && nvm use`, then `npm ci`. Commit `package-lock.json`;
Yarn's old SDK 49 lockfile has been replaced so there is only one dependency lock.

For the fresh Pixel 10 emulator, you can also run this in a separate terminal:

```bash
./scripts/mobile emulator
```

Then press **a** in the Metro terminal to open the app. This launcher cold-boots
without loading a saved graphics snapshot; it does not wipe the device's data.

## Backend

Simulator defaults:

| Environment | Django API origin |
|---|---|
| iOS Simulator | `http://127.0.0.1:8000` |
| Android Emulator | `http://10.0.2.2:8000` |
| Physical device | `https://direct2logbook.com` |

Run Django locally before signing in. If Android gets `DisallowedHost`, add
`10.0.2.2` to the **local development** Django allowed hosts. Do not change
production allowed hosts for this. Requests time out after 15 seconds.

To override the origin, set `EXPO_PUBLIC_API_URL` in your ignored `.env` and
restart Metro. For example, explicitly opt into the production API with:

```dotenv
EXPO_PUBLIC_API_URL=https://direct2logbook.com
```

Anything named `EXPO_PUBLIC_*` can be embedded in the client app; never use that
prefix for passwords, private keys, Sentry upload tokens, or API auth tokens.

## Development builds (later)

These compile the app itself and require current platform tooling:

```bash
./scripts/mobile ios
./scripts/mobile android
./scripts/mobile start
```

`start` connects to your own development build; `go` connects to Expo Go. Native
projects are generated by Expo and ignored in Git. Original SDK 49 Android files
were preserved under `/tmp/d2lb-android-sdk49-20261104` on this Mac. Native
compilation, signing, stores, and EAS publishing are separate from Expo Go.
Existing app slug, owner and Android package ID are retained.

## App versions and releases

`package.json` is the source of the visible app version. `app.config.js` supplies
it to Expo while preserving the other settings in `app.json`. About shows this
version with **Development** in Expo Go. Installed apps show their native version
and build number, so an updated JavaScript bundle cannot mislabel the installed
binary. Expo Go's own version/build are never shown as the app's version.

After a merge to `main`, GitHub's **Prepare mobile release** workflow
checks the app and lets Release Please maintain a release PR. Use conventional
PR titles and **Squash and merge** for feature branches:

| PR title | Version change |
|---|---|
| `fix: correct flight dates` | Patch, for example `0.1.0` → `0.1.1` |
| `feat: add aircraft defaults` | Minor, for example `0.1.1` → `0.2.0` |
| `feat!: change the sync contract` | Major, for example `0.2.0` → `1.0.0` |
| `docs: explain setup` or `chore: update tooling` | No release by itself |

PR checks validate the title. GitHub's default squash commit title is set to the
PR title; keep that title when merging so Release Please sees the same category.
Use `!` only for a breaking change. Multiple merged changes accumulate in one
release PR, with the highest applicable version bump.

The release PR updates `package.json`, `package-lock.json`, the release manifest,
and `CHANGELOG.md`. The workflow **automatically merges it after its checks pass**,
then creates the Git tag and GitHub Release. It does not build or submit an
app to Apple or Google, or publish an Expo update. The initial manifest is
`0.0.1`; `last-release-sha` in `release-please-config.json` excludes development
history before this setup, including history after the old `v0.0.1` tag.
Once a new release exists, its newer tag becomes the starting point instead.
Release Please handles subsequent version changes.

The workflows use GitHub's built-in token; no new token or secret is needed.
Repository Settings → Actions → General must allow GitHub Actions to create
pull requests (already enabled for this repository). The release workflow calls
**Mobile checks** directly on the release PR's exact commit, with read-only
permissions, so bot PR workflow approval prompts do not block the release.
Only the release bot's PR on its designated branch can merge automatically.
The guard allows only version changes in the package files and release manifest,
plus the changelog. It rechecks the PR and main before merging and will not merge
a changed head using an older successful check. Ordinary feature PRs are still
merged normally. A failed release check leaves its PR open; after resolving the
failure, retry **Prepare mobile release** on `main` from Actions → Run workflow.
Existing release PRs are refreshed from main and checked again on retries,
including when only CI or documentation changed. Tagging runs in
the same workflow because a merge by GitHub's built-in token does not start
another push workflow.

Before shipping a user-facing update, replace the highlights in
`app/components/updateNotes.js` and give the announcement a new ID. The app
shows those notes once per device after startup. Keep the same ID for rebuilds
of the same update so testers who dismissed it do not see it again.

Native build numbers are separate. `eas.json` already uses remote version
management and `production.autoIncrement: true`: each production EAS build gets
a new Android version code/iOS build number. A merge or Expo Go reload does not
consume a build number. When preparing our first store build, initialize or
check EAS's remote counter against any previously uploaded build numbers using
`eas build:version:set`. Development/preview profiles keep their existing setup.

## Sentry

The legacy `sentry-expo` package and obsolete publishing hook were replaced with
`@sentry/react-native`. Upload credentials must be supplied as `SENTRY_AUTH_TOKEN`
to native build tooling, never stored in app.json. Revoke the old upload token
that was previously committed; removing it from current files does not remove
Git history. Development error reporting is disabled to keep test errors out of
production Sentry. Source-map upload and native Sentry are not verified by a
JavaScript export or an Expo Go launch.

current offline-first implementation status. On `mobile/01-offline-first`, flight
changes are saved to SQLite and queued locally, then uploaded through the new
acknowledged sync API. The matching Django branch must be deployed and migrated

create/restart/sync/edit/delete acceptance test. The old AsyncStorage
queue is retained separately for review.

Sentry build tooling (glob and minimatch), and no high/critical findings. Its
suggested forced fix would downgrade Expo; do not run `npm audit fix --force`.
Review upstream patches before release.
